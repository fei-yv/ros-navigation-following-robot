# ROS 导航小车项目技术报告

作者：fei-yv　　日期：2026-09

## 摘要

本项目制作了一台基于 ROS Noetic 的室内移动机器人，主要完成二维激光建图、地图导航、多点导航和人员跟随等功能。小车采用 Wheeltec C30D mini_diff 差速底盘，搭载 Camsense X1 360°激光雷达、板载计算主机和罗技 C930c 摄像头。软件方面使用 ROS 作为通信和运行框架，底盘节点负责串口通信、速度控制和里程计发布，gmapping 负责实时建图，AMCL 与 move_base 负责定位和路径规划，人员跟随部分使用 YOLOv8n 模型导出的 ONNX 文件进行目标检测。项目总成本约 800 元。调试过程中重点解决了串口设备识别、编码器方向、TF 坐标关系、激光无效点处理和远程 RViz 显示等问题。最终完成了多点导航实测，连续运行约 2 分 42 秒，过程中没有发生碰撞；人员跟随功能也已经完成。测试表明，系统能够满足室内基础导航和跟随任务，但受低成本雷达回波质量、差速底盘转弯打滑以及小主机性能限制，转弯时仍可能出现少量地图重影，后续还需要进一步提高传感器和底盘标定精度。

关键词：ROS Noetic；gmapping；AMCL；move_base；多点导航；YOLOv8n；ONNX

## 1 项目目标与总体方案

本项目的目标是完成一台能够自主感知环境、建立二维栅格地图、按照目标点导航，并在摄像头识别到人员后进行跟随的移动小车。考虑到项目经费和已有设备，方案没有采用昂贵的工业雷达和高性能工控机，而是以现有差速底盘、360°激光雷达和低功耗小主机为基础，在 ROS 中搭建完整的软件链路。

系统采用“底盘负责运动，雷达负责环境感知，ROS 负责模块通信”的分层结构。建图阶段启动底盘、雷达、robot_pose_ekf 和 gmapping。底盘发布轮式里程计 `/odom`，雷达发布 `/scan`，robot_pose_ekf 根据里程计发布 `odom_combined -> base_footprint`，gmapping 读取激光和 TF 后发布地图以及 `map -> odom_combined`。导航阶段停止 gmapping，改由 map_server 读取保存的地图，AMCL 根据激光进行定位，move_base 进行全局和局部路径规划，最终向底盘发送 `/cmd_vel`。

人员跟随与导航相互独立。摄像头采集图像后由人员检测节点运行 YOLOv8n，检测结果转换为目标在图像中的位置和距离信息，再通过速度控制节点产生低速跟随指令。由于小主机 CPU 不支持 AVX/AVX2，未在小主机上安装完整 PyTorch 运行环境，而是使用已经导出的 ONNX 模型配合轻量推理方式，避免运行时因指令集不兼容而崩溃。

小主机运行 Ubuntu 20.04 和 ROS Noetic，内存约 4 GB。它的优点是体积小、功耗低、便于安装在车体上；缺点是 CPU 性能有限，且没有 AVX/AVX2 指令集，不适合直接运行官方 PyTorch 版 YOLO。Camsense X1 的理论量程约 8 m，实际有效回波会受到墙面材质、反射角度、环境遮挡和雷达安装高度影响。实际测试中有效点主要集中在较近距离，因此报告中的量程只写硬件上限，不把理论值当作实际稳定测量值。

## 3 机械结构与安装

车体采用上下两层亚克力板结构。下层安装 C30D 底盘、电池和底盘控制相关部件，上层通过铜柱与螺丝固定在下层上方，小主机安装在上层中心附近，顶部安装激光雷达，摄像头安装在便于观察前方的位置。亚克力板根据底盘孔位进行打孔，再用铜柱调整上下层间距。这样的结构加工简单、成本低，也方便后续拆装和更换设备。

机械安装时重点考虑了三点。第一，雷达应尽量水平，周围不能被亚克力板或线缆遮挡，否则会形成固定角度的盲区。第二，小主机和电池尽量位于车体中心附近，避免重心偏向某一侧导致转弯时脚轮受力不均。第三，摄像头与雷达的线缆需要固定，防止小车运动时线缆摆动进入雷达扫描范围。底盘为差速结构，前进和转弯的运动模型与麦克纳姆轮不同，转弯时脚轮和地面之间会产生额外摩擦，因此应采用较低角速度并尽量减少原地急转。

## 4 软件架构与 ROS 通信

软件平台为 Ubuntu 20.04 + ROS Noetic。项目工作空间中主要使用 `turn_on_wheeltec_robot`、`wheeltec_robot_rc` 和 `camsense_driver` 等功能包。启动底盘后，底盘节点通过串口接收控制帧并发布 `/odom` 和 `/imu`，同时订阅 `/cmd_vel`。为避免控制帧中断后小车继续运动，底盘程序加入了通信异常时自动停车的逻辑。

系统的核心 TF 链为：

```text
map -> odom_combined -> base_footprint -> laser
```

其中 `map -> odom_combined` 在建图时由 gmapping 发布，在导航时由 AMCL 发布；`odom_combined -> base_footprint` 由 robot_pose_ekf 根据轮式里程计发布；`base_footprint -> laser` 为静态 TF，描述雷达相对车体的位置。RViz 运行在笔记本上，小主机运行 ROS 主节点，两台设备通过网络共享 ROS_MASTER_URI。远程运行时，RViz 的 Fixed Frame 设置为 `map`，否则地图、激光和机器人模型会出现坐标不一致。

底盘标定中使用了约 1.022 的前进方向里程计修正系数，横向保持约 1.0，旋转相关正负方向使用约 1.019 的修正系数。这些系数不是通用常数，而是根据当前底盘和场地测试得到的工程参数。板载 IMU 能够稳定发布约 20 Hz 的数据，但由于存在零偏，当前方案没有直接把 IMU 融合进建图定位，避免静止或直行时陀螺仪偏置造成航向漂移。

## 5 建图实现与问题处理

建图使用 `slam_gmapping`。当前主要参数包括：地图分辨率约 0.1 m，`maxUrange` 约 6 m，`maxRange` 约 8 m，粒子数约 20，匹配迭代次数约 5，`lskip` 约 2，线位移更新阈值约 0.05 m，角度更新阈值约 0.1 rad，时间更新约 1 s。分辨率调到约 0.1 m 后，小主机上的 CPU 压力明显比 0.05 m 时低，适合当前低功耗平台。

调试时最明显的问题是运动过程中出现重影，以及以小车为中心出现一个会随车移动的大白色圆形区域。排查 `/scan` 后发现，雷达质量值为 0 的无效测量在驱动中被写成距离 0。对于 gmapping 来说，距离 0 不是“未知”，而是“近处存在障碍物”，因此这些无效点会被错误地写入地图，造成未扫描区域被清空。修复方式是在 `camsense_publisher_node` 发布 LaserScan 时，把 `quality=0` 的点改为 `NaN`，让 gmapping 按未知数据处理。

修复前约有 180 个 0 值点；修复后 0 值为 0，NaN 约 214 个，移动的大白圆消失，地图的未知区域恢复为灰色。后续统计中，一圈约 400 个点里有效点数量会随环境变化，某次测试有效点约 186 个，最大有效距离约 2.91 m。这说明地图可见范围并不等于驱动声明的 8 m，实际回波还受到场地和障碍物反射特性的影响。建图时还发现转弯比直行更容易出现重影，因此实际操作采用低速直行、缓慢转弯，并尽量沿已经走过的路线回访以帮助闭环修正。

## 6 导航与多点导航实现

完成建图后使用 `map_server` 保存地图，导航阶段启动 AMCL、move_base、底盘和雷达，停止 gmapping，避免两个节点同时发布 `map -> odom_combined`。启动 RViz 后将 Fixed Frame 设置为 `map`，先使用 `2D Pose Estimate` 设置机器人初始位置和朝向，再使用 `2D Nav Goal` 发送单个目标点。AMCL 根据激光扫描和已有地图估计机器人位姿，move_base 先在全局地图上规划路线，再利用局部代价地图实时避开障碍物。

多点导航是本项目的重点功能，采用 [6-robot/waterplus_map_tools](https://github.com/6-robot/waterplus_map_tools) 航点插件保存和读取航点文件。航点由 RViz 中的 Add Waypoint 工具添加，保存为 XML 文件后交给多点导航节点按顺序执行。本仓库使用其公开接口，不包含该插件源码；原项目采用 GPL-2.0 许可证，使用时应遵循原项目许可。实际使用时，先确认小主机上的 ROS 节点已经启动，再在笔记本上打开 RViz；随后加载地图、设置初始位姿并检查机器人模型和激光是否重合。发送多点任务前，先清理旧的导航进程和旧目标，防止重复的 move_base 或航点节点产生冲突。完整命令见[常用运行命令](../docs/commands.md)。

本次实车测试使用已经保存的地图完成多点导航，任务总用时约 2 分 42 秒，过程中没有发生碰撞。由于测试重点是功能完成和运行稳定性，报告不虚构导航距离、定位误差和规划成功率等没有专门测量的数据。实际运行中，地图质量、初始位姿精度和无线网络延迟都会影响导航表现，尤其是在远离无线路由器后，远程 RViz 可能出现数据延迟或连接中断。

## 7 人员跟随功能

人员跟随部分使用罗技 C930c 摄像头获取前方图像。检测模型选用 YOLOv8n，因为它是 YOLOv8 系列中较轻量的模型，适合只关注“person”类别的低速跟随任务。原始权重文件为 `yolov8n.pt`，在具备完整 Python 深度学习环境的电脑上导出为输入尺寸约 320×320、ONNX opset 约 12 的 `yolov8n.onnx` 文件，文件大小约 13 MB。

小主机 CPU 不具备 AVX/AVX2 指令集，直接安装 PyTorch 和 Ultralytics 可能在导入或推理时触发非法指令，因此没有把完整 YOLO 运行环境部署到小主机。实际采用的思路是将模型转换成与框架解耦的 ONNX 文件，再由轻量推理程序读取摄像头图像并输出检测框。控制逻辑根据人员在图像中的水平位置调整转向，根据目标框大小或距离估计调整前进速度；当目标短时间丢失时降低速度或停车，避免小车继续盲目前进。

人员跟随功能已经完成，能够与底盘速度控制配合运行。当前没有对不同光照、遮挡、多人场景下的识别率和帧率进行系统统计；后续可以增加检测频率、跟随距离和丢失目标停车时间等参数的记录，使结果更容易量化。

## 8 实测结果、不足与总结

从目前测试结果看，系统已经完成主要功能的基本实车演示：底盘能够通过键盘或 ROS 速度指令运动，雷达能够发布有效扫描，gmapping 能够建立二维地图，保存的地图可以用于 AMCL 和 move_base 导航，多点导航有一次约 2 分 42 秒、无碰撞的实测，摄像头人员跟随也已完成。速度、续航和不同场地的运行表现尚未系统量化，因此报告只记录已经实际完成的功能，不把未测数据写成结论。

项目中最耗时的部分不是单个节点的编写，而是各模块之间的时间戳、坐标系和数据含义必须一致。激光无效点不能用 0 代替、静态 TF 不能重复发布、建图和导航不能同时发布同一条 TF，这些问题一旦出现，表面上看起来像是算法效果不好，实际上是底层数据错误。通过查看 `/scan`、`/odom`、`/imu`、TF 和节点 CPU 占用，逐步把问题定位到驱动数据和运动模型，而不是盲目反复更换算法。

当前仍存在一些不足。差速底盘转弯时脚轮摩擦和轮胎打滑会造成里程计误差，gmapping 在转弯阶段更容易出现轻微重影；Camsense X1 的有效回波距离受环境影响较大，理论 8 m 不能保证每个方向都能稳定测到；小主机性能有限，建图分辨率过高或同时运行多个视觉节点时可能出现 CPU 峰值；远程 RViz 还依赖无线网络质量。后续改进应优先进行轮径、轮距和雷达安装位姿标定，规范转弯速度，并对不同场地重复测试，而不是只看单次地图截图。

总体而言，本项目完成了从机械装配、底盘驱动、传感器接入，到 SLAM 建图、导航和人员跟随的完整闭环。通过这次实践，我对 ROS 节点通信、TF 坐标变换、激光数据格式和导航栈的关系有了更直观的认识，也认识到低成本硬件下“数据正确”比单纯增加算法参数更重要。当前方案保留 gmapping，主要因为它在现有设备上能够稳定运行，且部署简单、资料较多；同时通过修复无效雷达点、调整地图分辨率和规范操作方式，使系统达到了可运行、可展示、可复现的状态。
